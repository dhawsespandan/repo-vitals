# WP-1 Method Note

Weights for the four risk signals (deprecation, vulnerability severity, vulnerability count, and version staleness) were derived using an informal application of AHP principles. A pre-filled seed matrix (from the project's earlier design work) was reviewed in a single joint session; each of the six pairwise judgments was individually evaluated and retained without modification (see per-cell rationale in `wp1_tier1_weights.yaml`). The principal eigenvector of this matrix was computed via eigenvector decomposition and normalized to yield the weight vector. Because the seed matrix was adopted unmodified, its Consistency Ratio (CR = 0.0115) is inherited, not earned from independent judgment — a CR that low is the signature of a generated ratio scale, not a contested human assessment. CR is a coherence check on the judgments, not a correctness check on the weights (Appendix B); correctness is addressed by WP-6's validation. However, these weights were not independently cross-validated: both judgments were made in a single joint pass rather than by independent judges with a formal reconciliation step. A fully validated derivation using independent judges, reconciliation, and an entropy-weighting cross-check is presented as the Tier-2 study (WP-3). The npm eigenvector truncates deprecation slightly (0.4673 → 0.46) so the published vector sums to exactly 1.00. These weights enter the per-occurrence scoring formula `100 − 100·(Σ wᵢ·Sᵢ)` defined in the implementation plan (§5.2).

**PyPI decision.** A separate weight vector was produced for PyPI. npm's deprecation field carries a free-text message (often naming a successor package), making it a high-information, zero-ambiguity signal. PyPI's equivalent mechanisms — release yanking and the "Development Status :: 7 - Inactive" classifier — are real but carry less information: yanking is per-release rather than per-package, and the Inactive classifier is rarely applied in practice. Accordingly, the PyPI vector reduces the deprecation weight by approximately 30% (0.46 → 0.32) and redistributes that mass to severity and staleness, which serve as stronger risk proxies in the PyPI ecosystem where explicit deprecation signals are weaker. Count is left at 0.16; the redistribution shifts its rank relative to staleness (count outranks staleness 0.16 vs 0.10 on npm, but falls below it 0.16 vs 0.17 on PyPI) — this is accepted as a consequence of staleness gaining mass, not of a change in count's own assessment. The redistribution also causes severity (0.35) to overtake deprecation (0.32) as the top-weighted PyPI signal; this inversion is intentional — in an ecosystem where explicit deprecation markers are weak and rarely applied, the severity of known vulnerabilities is the strongest available evidence of dependency risk and should dominate the score. The resulting PyPI vector (deprecation 0.32, severity 0.35, count 0.16, staleness 0.17) still sums to 1.00, and no weight is 0 or exceeds 0.6. This PyPI derivation is a known limitation (L6): the vector comes from the same session by reasoned redistribution, not from an independent PyPI-only calibration; the S1 PyPI sanity analysis (§2.4.6) is the mitigation.
