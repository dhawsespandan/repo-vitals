## Abstract

We present RepoVitals, an open-source web tool that scores the dependency health of a GitHub repository (npm and PyPI) on a deterministic 0–100 scale and then writes remediation plans grounded in each package's own changelog and README.

- **The score.** It combines four registry and vulnerability-database signals through a published, versioned formula, with a rank-decayed roll-up in which clean dependencies cannot dilute risky ones. Every flagged dependency has a drill-down showing the arithmetic.
- **The remediation.** It is generated by an LLM agent behind a deterministic grounding gate. Its plans show the retrieved passages beside the citations that use them, and say so when the sources are too thin.
- **Safety.** The tool never writes to a repository.

Beyond the product, RepoVitals is a research instrument. Every scan is kept as permanent research history tagged with the weights version that scored it, and every remediation leaves a full trace. A management-command layer builds a stratified corpus, validates the formula, and runs a paired retrieval experiment over the same code paths the product uses. We describe the design, its two-ecosystem adapter seam, and the evidence released with it.

## 1. Motivation

Developers learn about risky dependencies from tools whose verdicts they cannot inspect. RepoVitals is built around three commitments:

1. **The number is deterministic and explainable.** No model touches it. Each signal's contribution is shown and sums to the score.
2. **Generated advice is checkable.** Every remediation is shown beside the exact source text it was generated from.
3. **The tool cannot change your code.** There is no write path to GitHub. A plan can be downloaded as Markdown or JSON as a handoff, not a commit.

## 2. The tool

**Scanning.** The user signs in with GitHub and registers a repository they can push to. A scan does the following:

1. Walks the default branch's tree and finds every supported manifest:
   - npm `package.json` with its lockfiles;
   - PyPI requirements files, `pyproject.toml` (PEP 621 and Poetry), `setup.py`/`setup.cfg`, Pipfile and Poetry locks.
2. Resolves every declared dependency against its registry.
3. Queries OSV for advisories on the resolved version.

Dependencies that cannot be resolved (git URLs, local paths) are listed with reasons and kept out of the score.

**Scoring.** For each occurrence the tool computes penalty = 100 × (w_dep·deprecated + w_sev·CVSS/10 + w_cnt·min(n,10)/10 + w_stl·min(days,1095)/1095), with per-ecosystem weights.

The repository score is 100 − Σ_k p_k·0.5^k over the penalties sorted worst first, clamped to [0, 100]. It is classified Safe (≥ 80), Medium (50–79) or High alert (< 50). The roll-up has three properties:

- The worst dependency counts in full.
- Every further risky dependency adds a diminishing share.
- A clean dependency adds nothing, so it cannot dilute the rest.

The weights file is versioned, and every stored score names its version. The current weights (v2) come from an AHP study, validated against entropy weights, perturbation and known-bad anchors (study S1).

**Remediation.** Two report types:

- **A repo-wide triage summary.** It is validated so that every fix it names is a real scanned row.
- **A per-dependency plan from a small LangGraph agent.** It runs in four steps:
  1. Fetch the package's changelog and README.
  2. Chunk and embed them with fastembed, store them in embedded Chroma, and retrieve the top 5.
  3. Apply a deterministic gate: top-1 similarity ≥ 0.30 and ≥ 400 characters.
  4. Generate a JSON plan with chunk-id citations, using a Groq-hosted model at temperature 0.

Below the gate, the plan must open by saying it rests on the scan's own measurements. Reports are cache-first: a second click is served from the stored row with zero model calls. A per-key lock and a partial unique index ensure that a double-click pays for one generation.

**Projects and trends.** Repositories can be grouped into projects, and the combined report notes shared flagged dependencies across siblings. A trend chart shows every stored scan, with a marker where a new weights version took over.

## 3. Engineering for free tiers

The whole system runs on free tiers: Vercel (SPA), Render (one Django worker, 512 MB), Supabase (Postgres), Groq and Gemini. That constraint shaped the design:

- **Embeddings.** They use ONNX via fastembed rather than torch, which would be about 700 MB on its own. The model loads lazily and is shared by the whole process.
- **Batching.** Embedding runs one chunk at a time with ONNX Runtime's CPU arena disabled. This was measured necessary twice on production (decisions §8.15, §14.15). Batches of eight peaked at 553 MB on a 69 KB changelog; one at a time peaks at 352 MB and is faster.
- **Concurrency.** Background work runs in in-process threads behind polling endpoints. There is no Celery or Redis.
- **Same-origin routing.** The browser stays same-origin through a Vercel rewrite: one session cookie, no CORS, no JWTs. The GitHub OAuth token is encrypted at rest and never reaches the browser.

## 4. One pipeline, two ecosystems

PyPI was added as a second adapter behind one interface (`DependencyAdapter`). We treat "the core did not change" as a falsifiable claim and publish the diff (`docs/adapter_soundness.md`):

- The phase touched 7 application files (1,448 lines inserted).
- 1,125 of those lines are the two new files: the PyPI parsers and a PEP 440 grammar.
- The rest of the application changed by 323 inserted and 25 deleted lines in five named files.
- The scanner, the scoring engine and the API were untouched across the whole tag range.

## 5. A research instrument by construction

- **Permanent history.** Each completed scan writes research rows: repository-level and per-occurrence signals, `data_source` (`live_scan` or `corpus_scan`), and the weights version. Rescans and deletions never remove them. Analyses recompute scores from stored signals under any weights version rather than reading stored scores.
- **Corpus and validation.**
  - `build_corpus` draws a seeded, stratified, deduplicated sample: 914 repositories over 240 strata.
  - `scan_corpus` scores it with the production pipeline into a separate research database.
  - `validate_formula` runs the full S1 validation offline from that data.
- **Experiment.** `run_experiment` runs paired conditions over a frozen labelled set: no retrieval, single-pass retrieval, the production agent, and an internal broader-retrieval condition that cannot be reached over HTTP. `analyze_experiment` computes deterministic correctness and the prespecified tests.
- **Replication.** One command exports the research tables and signed deliverables. Two notebooks regenerate every study table from the export alone, and the test suite executes them against a synthetic export so they cannot drift from the code.

## 7. Limitations

- **Coverage.** Manifest-level only: no transitive resolution beyond lockfiles, and no reachability analysis.
- **Scope.** Only GitHub repositories the user can push to.
- **Remediation quality** is bounded by what each package publishes. Study S3 found that retrieval did not improve correctness over the scanner's own structured facts.
- **Free tiers.** Cold starts take about 50 s, and generation is paced by rate limits.
