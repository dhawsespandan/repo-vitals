# Replicating RepoVitals and its two studies

This file is the replication package's manual (§10 Phase 14). It says what was
measured, with which code, models, seeds and weights; how to regenerate every
table and figure the two studies report from what is committed here; and the
limitations that must travel with the data wherever it is used.

- **S1 — validated deterministic scoring:** is the AHP-derived,
  entropy-cross-checked risk formula internally consistent, externally
  convergent and robust? Results: WP-6's validation report.
- **S3 — retrieval grounding across ecosystems:** does retrieval improve
  remediation correctness and faithfulness, and does it degrade where an
  ecosystem's deprecation metadata says less (PyPI vs npm)? Results: WP-8's
  runs and tables, with WP-9's judge validation.

The study designs are in `plan/repo_vitals_research_plan.md` (File C); every
engineering decision behind the numbers is in `docs/decisions.md`, cited here
by section (§11.29 is decision 29 of Phase 11).

---

## 1. What can be reproduced, and what is a record

The data was collected once, from live services, and **the committed files
are the record of what those services said on the day.** Everything computed
*from* that record regenerates exactly; the collection itself can be re-run,
but would observe a different world.

| Step | Reproducible? | Why | The record |
|---|---|---|---|
| Corpus sampling (WP-4) | re-runnable, not reproducible | GitHub search results change daily | `wp/wp-4/corpus_manifest.json` |
| Corpus scan (WP-5) | re-runnable, not reproducible | registry and OSV state change daily | `wp/wp-5/wp5_research_db.dump` |
| S1 validation (WP-6) | **exactly**, offline | pure computation over the dump, with deps.dev's answers and the anchor scan recorded | `wp/wp-6/validation_report/` |
| `v2` scores of the corpus | **exactly**, offline | `rescore` over stored signals (D6) | regenerated in seconds |
| S3 labelled set | re-runnable, not reproducible | OSV and registries are asked again | `wp/wp-8/labelled_set.jsonl` |
| S3 generations (WP-8) | re-runnable, not reproducible | a hosted model at temperature 0 is not bit-deterministic, and Groq retires models | `wp/wp-8/runs/*/items.jsonl` |
| S3 correctness | **exactly**, offline | a program over the generations | regenerated by the notebook |
| S3 judge verdicts | re-runnable, not reproducible | a hosted judge; the cache is withheld (§9) | `wp/wp-8/runs/analysis/metrics.csv` |
| S3 tables (WP-8) | **exactly**, offline | `analysis.render` over correctness + recorded verdicts | `wp/wp-8/runs/analysis/` |
| WP-9 kappa | exactly, with the withheld key | | decisions §13.17 |

## 3. From a fresh clone to every study table

About 15 minutes, most of it installing packages. Nothing below needs a
GitHub token, an API key or the network after step 2.

**Prerequisites:** Python 3.11 for byte-exact output (3.12+ works; see §5),
Docker, Git.

1. **Install the frozen backend dependencies.**

   ```bash
   cd backend
   python3.11 -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
   pip install -r requirements-dev.txt
   ```

2. **Start the research database and restore WP-5's dump into it** — into the
   empty database the container creates; do not run `migrate` first, the dump
   carries its own schema.

   ```bash
   docker compose --profile research up -d research-db
   docker exec -i repovitals-research-db pg_restore -U repovitals -d repovitals_research --no-owner < ../wp/wp-5/wp5_research_db.dump
   ```

   Check it: `docker exec repovitals-research-db psql -U repovitals -d repovitals_research -c "select count(*), sum(risk_score) from scan_history"`
   must print **914 | 42161.55**, and `dependency_history` must hold
   **29,494** rows. The dump's sha256 is
   `82602febee9edecdea657773be420f0a8ba568b1bd19db18823e60206550276f`.

3. **Point the backend at it.** Create `backend/.env` with three lines (the
   two keys only have to be well-formed; nothing is signed or decrypted):

   ```
   DJANGO_SECRET_KEY=replication-not-a-secret
   TOKEN_ENCRYPTION_KEY=cmVwb3ZpdGFscy10ZXN0LWtleS1kby1ub3QtdXNlISE=
   DATABASE_URL=postgres://repovitals:repovitals@localhost:5433/repovitals_research
   ```

4. **Export.**

   ```bash
   python manage.py export_research_data
   ```

   This writes `research_data/exports/` — the three permanent tables as
   Parquet and CSV, the signed deliverables File C reads, the weights files,
   and `MANIFEST.json` with every file's sha256 and source — and archives the
   File B deliverables as received under `research_data/deliverables/`. It
   only reads the database (it runs inside a guard that refuses every write),
   exports `corpus_scan` rows only unless `--source` says otherwise, and two
   exports of one database are byte-identical whatever the database's locale.

5. **Run the notebooks.**

   ```bash
   cd ../notebooks
   jupyter execute --inplace 13_3_validation.ipynb 13_1_analysis.ipynb
   ```

   or open them in JupyterLab (`pip install jupyterlab`). Each one verifies
   the export against its manifest, regenerates its study's signed output with
   the harness's own code, and **asserts** that every regenerated file matches
   the signed copy. They run under `config.settings.offline`, whose database
   backend raises on the first query: the export is the only input.

   - `13_3_validation.ipynb` (S1, legacy id 13_3): rebuilds the corpus panel,
     checks that all 914 stored scores reproduce under their own weights
     version, tabulates the corpus under `v0_equal`/`v1`/`v2`, re-runs WP-6's
     `validate_formula` offline from its recorded `inputs.json`, and compares
     the report and all nine data files. About 45 s.
   - `13_1_analysis.ipynb` (S3, legacy id 13_1): recomputes correctness for
     all 450 generations, compares it with the signed `metrics.csv`, and
     re-renders `tables.md` and its seven CSVs. About 5 s.

The suite runs both notebooks end to end against an export built by the real
commands (`backend/tests/test_replication.py`), so they cannot drift from the
code they call.

## 5. Exactness: two things that change the last digits

**Python's `sum()`.** Python 3.12 made `sum()` of floats compensated
(Neumaier summation). The signed runs used 3.11, which regenerates every file
**byte for byte**. On 3.12 and later, every rounded table (`report.md`,
`tables.md`) is still identical, and three full-precision CSVs (`entropy.csv`,
`correlation.csv`, `confusion.csv`; S3's `precision.csv`) differ in the last
one or two digits of some cells. The notebooks report those files as *equal
to float precision* (relative tolerance 1e-12) rather than identical, and fail
on anything larger. Verified 2026-10-10 on 3.11.17 and 3.12 (decisions §14).

**The database's collation.** `validate_formula` loads the corpus ordered by
`repo_full_name` in the database's collation, and its seeded bootstrap
resamples repositories by position. WP-6 ran on Docker's `postgres:16`, whose
default `en_US.utf8` sorts names differently from `C.UTF-8`. Point estimates
do not depend on the order; the bootstrap intervals do, in their third
decimal. So:

- the **notebook** rebuilds the panel in WP-6's own order, read from the signed
  `scores.csv`, and reproduces the intervals on any machine;
- **re-running `validate_formula`** reproduces them only on an `en_US.utf8`
  database — which the Docker database in §3 is.

The export itself sorts text by byte value, so its files do not depend on the
collation at all.

## 9. Withheld, and why

- **The WP-9 answer key, both kappa reports, attempt 1's labels, and the full
  judge cache** stay with the developer until it is decided whether a fresh 50
  will be labelled (decisions §13.17); publishing them would unblind that
  labelling. The per-item verdicts are already in `metrics.csv`; the key maps
  `ITEM-001`… to them.
- **Archived manifest blobs** of the corpus and the anchors: they are other
  people's repository contents, re-fetchable by their recorded git SHAs.
- **Live-scan rows and agent traces** name RepoVitals users and possibly
  private repositories; the export leaves them out unless `--source` asks.

## 10. Limitations that travel with the data

Quote these wherever the numbers go. File C's L1–L12 are the full register;
these are the ones the delivered data made concrete.

**S3's judge**
- **The judge is not validated.** WP-9's Cohen's kappa is **0.134** (linearly
  weighted 0.186; raw agreement 34/50). File C §3.4.1 requires ≥ 0.50: the
  judge's faithfulness verdicts **cannot be used in S3 as they stand**. The
  judge is lenient (it flagged 4 of the 16 items the human found unsupported),
  and its rule 4 accepts "not enough information" without checking MEASURED
  DATA. The two ways forward — tighten the rubric, re-judge all 450 and
  re-validate on a fresh 50; or report faithfulness from the 50 human labels
  only — are decisions §13.17's, not yet taken. Correctness is deterministic
  and unaffected.

**S1's weights**
- **One judgment.** "The Tier-2 AHP weights were derived from a single
  pairwise-comparison judgment (CR = 0.0054). The two-judge protocol with
  reconciliation planned in the work plan was not carried out, so the vector
  has no inter-judge agreement behind it; the entropy-derived vector computed
  from the 914-repository corpus is the independent cross-check."
- **PyPI's vector is not independently calibrated** (L4): it is the AHP vector
  shifted by a reasoned rule from the same session.
- **H1 is not supported:** AHP vs entropy cosine 0.898 (npm), 0.691 (PyPI), top
  two signals differing in both; PyPI's entropy weight on deprecation (0.515)
  comes from rarity (48 of 8,922 occurrences).
- **H2 is not supported:** Spearman ρ against deps.dev's Scorecard is 0.047
  [-0.077, 0.169], on the 289 of 914 repositories (32%) deps.dev covers; no
  weighting of the four signals reaches ρ 0.2 (decisions §12.19).
- **Score falls with dependency count** (ρ −0.51 on the anchors); control for it
  before any comparison across ecosystems or repository sizes. Healthy-seeded
  outliers are driven by `examples/` and `docs/` manifests, which the scanner
  reads by design.
- **The OSV reference is circular** (L1): OSV supplies two of the four signals.

**The corpus**
- **One cross-section** (L12), as of 2026-10-07: nothing here supports a
  temporal, evolutionary or causal claim.
- GitHub only, JavaScript/TypeScript and Python, ≥ 5 stars, forks and archives
  excluded (L9); admission rate 68% (npm 83%, PyPI 57%), above File B's 40–60%
  and explained in `wp4_signoff.md`; 307 search cells stay over GitHub's 1,000-
  result cap at the deepest split and are sampled from their first 1,000 by
  stars.
- Manifest-level only: no transitive dependencies, no call sites (L10);
  unassessable occurrences 2.3%, listed and excluded rather than dropped.
- Missing CVSS scores take a 5.0 placeholder flagged as reduced confidence;
  §5.2's NVD fallback was not built (decisions §12.13). EPSS is collected
  behind a flag and never scored (D3).

**S3's design**
- **TARGET hands over most answers** (decisions §13.2, §13.13): every condition
  is shown each advisory's fixed version and the deprecation sentence. Only 22
  of the 150 items need the answer worked out; their table is a separate Holm
  family.
- **PyPI retrieval is mostly READMEs** (decisions §13.14 (4)): precision@k near
  zero on the PyPI arm. A threat to validity for that arm and for RQ3.
- **No PyPI replacement items:** none of the corpus's 34 deprecated PyPI
  packages names a successor, so PyPI's half is all `cve_fix` (L7); the
  `cve_fix` stratum is the controlled ecosystem comparison.
- One generator and one embedding model (L8). Generation was split across four
  team members' free-tier Groq accounts, one at a time, with model, prompts,
  temperature and pacing unchanged (`wp8_run_log.md`, L11). One B npm item has
  no precision@k verdict. Condition D (issue retrieval) was not run.
- Correctness scores the structured highest-priority fix, not the prose, and
  abstaining is never correct (decisions §13.6).
